1. WHAT SECURITY FEATURES *ARE* IMPLEMENTED:
------------------------------------------------------------------------
The developer has implemented the following technical security controls:

  - PASSWORD SECURITY: User passwords are encrypted using 12 rounds of 
    Bcrypt hashing. They are mathematically un-decryptable on disk.

  - SIGNATURE CRYPTOGRAPHY: Handwritten and uploaded signatures are 
    securely encrypted inside the database file using AES-128 (Fernet) 
    encryption before being written to disk.

  - SYSTEM LOCKDOWN AUTO-BLUR: When the administrative system lockdown 
    is active, signature decryption is suspended for all non-root users, 
    and images are forced into a mathematically irreversible server-side 
    Gaussian blurred state before leaving the host computer.

  - SOFT-DELETE / ARCHIVE CONTROLS: Temporarily hides cluttering or legacy 
    records from directory views without erasing their transaction data, 
    preserving 100% of their billing and official receipt (O.R.) counts 
    for system-wide financial audits.

  - STRICT O.R. FORMAT ENFORCEMENT: Enforces strict data validation on 
    Official Receipt (O.R.) inputs, allowing only structured 7-digit 
    numeric patterns (e.g., 1234567) to prevent unstructured data entries 
    and SQL injection attempts.

  - CHRONOLOGICAL AUDIT DATA: Automatically tracks record creations and 
    validated updates (`created_at` and `updated_at` columns) to ensure 
    that directory sorting is sequentially tracked and auditable.

  - CORS-SAFE DYNAMIC PDF NAMING: Uses native framework configurations to 
    safely update browser tab titles on PDF export, bypassing browser CORS 
    iframe sandboxing rules without exposing the parent frame window.

  - REAL-TIME AUDIT TRAIL LOGGING: Automatically logs all insertions, 
    updates, deletions, archives, unarchives, and signature decryptions, 
    including the operator's name, role, timestamp, target ID, client IP 
    address, and device details.

  - LOCAL FILE LOCK: On launch, Windows NTFS file permissions (via icacls) 
    are automatically set to block other local Windows user accounts from 
    opening the database or configuration files.

  - TRANSACTION BACKUPS: The database silently duplicates itself to your 
    designated local backup directory or external USB storage every time 
    a database modification is committed, secured by an atomic OS-swap 
    and structural integrity validation (PRAGMA integrity_check).

2. WHAT IS *NOT* IMPLEMENTED (DO NOT ASSUME THESE EXIST):
------------------------------------------------------------------------
  - NO MULTI-FACTOR AUTHENTICATION (MFA): The system relies entirely on 
    standard username/password login.

  - NO AUTO-LOGOUT TIMER: If a user leaves their browser tab open on a 
    shared PC, the session remains active indefinitely until they manually 
    click "Logout", are kicked by a Super Admin, or close the browser tab.

  - NO NETWORK-LEVEL FIREWALLS/IDS: The system does not detect or block 
    malicious network scanning or Denial-of-Service (DoS) attacks.

  - NO AUTOMATED SERVER-SIDE SYSTEM AUDITING: If the host operating system 
    is compromised at the root level, this application cannot detect it.

  - NO PHYSICAL ENCRYPTION FOR SQLITE FILE: The "app_database.db" is not 
    internally encrypted on the hard drive. While NTFS permissions block 
    unauthorized accounts, anyone with physical access or local admin 
    rights can copy the database. Full-disk encryption (such as BitLocker) 
    must be enabled manually by the department's system administrator.

  - NO DATA RECOVERY SERVICES: While automated local backups are performed 
    to your backups directory on database saves, the developer is not 
    responsible for restoring corrupted database files, restoring unmounted 
    drives, or recovering lost encryption keys.
